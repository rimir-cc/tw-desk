# Binary tiddlers: externalize, internalize and derivatives – design

Date: 2026-11-04 · Status: draft for review

## Why

The user imports binaries (images, PDFs, Office files, …) into their folder wikis with TiddlyWiki's standard import,
which keeps the content inside the wiki. In a folder wiki such a tiddler sits in `tiddlers/` as the binary file plus a
`.meta` file (or base64 inside a `.tid`/`.json`), so it is loaded into every browser tab and committed to git. The wikis
get **huge and slow**, and the **git repos bloat**. The user's Bitbucket (on-prem) has Git LFS switched off.
**Other people clone the wikis from Bitbucket**, so for now externalized files are **committed with the wiki** by
default; keeping `files/` out of git (backed up separately by the user) is a per-wiki option. With the default,
externalizing fixes the slowness but not repo growth – that waits for LFS or the "out of git" option.

Existing binaries come from standard import and the user's `rimir/drop-attach` plugin: both store them as binary file +
`.meta` in `tiddlers/` (no files in `files/` today).

On top, TW Desk should produce **derivatives** of each binary – thumbnail, page images, extracted text – as ordinary
tiddlers, so the content becomes visible and searchable. **Displaying** them is the user's job (their own plugins);
TW Desk only produces data.

## Goals

1. **Scan** every managed wiki regularly for binary tiddlers whose content is stored inside the wiki (and for
   `_canonical_uri` tiddlers whose file lies in `files/`). Show the result per wiki row as a chip, e.g.
   "23 embedded · 48 MB". The scan runs on a timer (like the git checks) and when a wiki stops.
2. **Per-wiki policy** (Edit dialog, stored in `config.json` on the wiki entry), one of:
   - **leave as is** (default for every wiki),
   - **externalize**: move the binary content to `files/<name>`; the tiddler keeps all its fields and gets
     `_canonical_uri: files/<name>` and an empty text,
   - **internalize**: the reverse – read `files/<name>` back into the tiddler and drop `_canonical_uri`.
   The policy is applied **automatically when the wiki stops** (before auto-commit on stop), and on demand with a
   button. It never runs while the wiki is running.
3. **Git handling of `files/`** – per wiki setting:
   - **commit with the wiki** (default): nothing special, `files/` is committed like the rest (auto-commit on stop
     includes it),
   - **keep out of git**: TW Desk adds `files/` to the wiki's `.gitignore`. Files already tracked stay tracked
     (TW Desk never runs `git rm --cached` – that would delete them on other clones at their next pull); the dialog
     says so.
   TW Desk never rewrites git history. Since others clone the wikis, everything must work on a clone that has the
   tiddlers but not (yet) the files: a missing `files/…` file means "not on this machine", never "deleted".
4. **Derivatives** (per wiki, on/off per kind, default off): for each binary, TW Desk writes generated image files to
   `files/.derived/…` (follows the wiki's `files/` git setting) and adds small tiddlers that point at them:
   - `<title>/thumb` – thumbnail (image with `_canonical_uri`),
   - `<title>/page/<n>` – one image per PDF page, pptx slide, docx page; for xlsx per printed page of each sheet,
     `<title>/sheet/<sheet name>/<n>`,
   - `<title>/text` – extracted text, `type: text/plain`, **stored in the wiki and committed** (it's what makes the
     content searchable).
   Every derivative tiddler has `derived-from: <title>` (and a field marking it as generated by TW Desk, so TW Desk
   can update or remove its own tiddlers and never touches the user's). The original gets summary fields such as
   `page-count`.
5. **Sources and how** (all in-app, no user-installed tools needed except LibreOffice for Office pages):

   | Source | thumb | pages | text |
   |---|---|---|---|
   | images (png, jpeg, gif, webp, avif, svg, bmp) | Chromium in a hidden window (canvas) | – | OCR (tesseract.js, deu + eng) |
   | PDF | pdf.js page 1 | pdf.js, every page | pdf.js text layer; OCR when a page has no text |
   | pptx / docx / xlsx | embedded `docProps/thumbnail.jpeg` if present, else page 1 via LibreOffice | LibreOffice → PDF → pdf.js | from the zip's XML (no LibreOffice needed) |
   | legacy doc / xls / ppt | via LibreOffice | via LibreOffice | via LibreOffice → PDF → pdf.js |
   | audio, video, other | – | – | – |

   Derivatives are (re)generated when the original changes (content hash), and removed when the original is gone.
   Work runs in a background queue, one item at a time, like `webQueue`.
6. **LibreOffice, optional**: TW Desk uses an installed LibreOffice if found. Otherwise Settings offers
   **Install LibreOffice**: download the official MSI from documentfoundation.org, verify its checksum, and unpack it
   per user without admin rights (`msiexec /a … TARGETDIR=…`) into `<userData>/tools/libreoffice` (never the install
   folder – the uninstaller wipes that on every update). Conversion runs headless (`soffice --headless --convert-to pdf`).
   OCR language data (deu, eng) uses the same tools folder (downloaded once, or bundled if small enough – builder's call).

## Non-goals

- Shrinking existing git history (rewrite / force-push) – binaries already committed stay there.
- Git LFS support (off on the user's Bitbucket; could come later as another policy).
- Displaying derivatives in the wiki (user's plugins).
- Bundling LibreOffice into the installer (≈350 MB, >10,000 files with long paths – the exact thing that broke NSIS
  updates before; see CLAUDE.md "No asarUnpack").
- ImageMagick / Ghostscript (Ghostscript is AGPL; Chromium + pdf.js cover the common formats).
- Static HTML exports / single-file builds keeping externalized images (relative `files/` URIs only work when served).

## Anti-goals (failure even if it "works")

- Losing or corrupting a binary. Externalize writes the file into `files/`, verifies it (size + hash), and only then
  rewrites the tiddler; internalize likewise. A file name clash never overwrites a different file.
- Changing anything but the content location: title, type, tags, `created`, `modified`, `caption` and every other field
  stay as they are (`modified` is **not** bumped).
- Touching a running wiki's files, or the user's real wikis in tests.
- Writing into included folders' tiddlers by policy (see constraints).
- Blocking the UI or app quit with long OCR/conversion work.

## Constraints

- **Wiki must be stopped** for externalize/internalize and for adding derivative tiddlers: the TiddlyWiki server reads
  tiddler files only at start (same rule as Pull and moving plugins to the store). Generated image files may be written
  any time, since `files/` is served live. If the wiki is started while derivative work for it is pending, the work
  waits for the next stop (builder may instead write the tiddlers through the running server's HTTP API – builder's call).
- **Included folders** (e.g. `_shared/rr-core`): the server serves only the main wiki's `files/`, so binaries in
  included folders are **reported only**, not externalized, and get no derivatives in v1.
- On-disk shape: an externalized tiddler becomes a `.tid` file (fields + empty text) instead of `<file>` + `.meta`.
  Use TiddlyWiki's own rules for file names / existing `retain-original-tiddler-path` where it matters (builder).
- External attachments the user already has (`_canonical_uri` pointing outside `files/`, or to http URLs) are left
  alone by internalize unless the file is local and readable inside the wiki folder.
- Code style and testing as in CLAUDE.md: plain JS, tabs, unit tests in `test/unit/` (Node test runner, electron stub),
  Playwright e2e in `test/e2e/` with temp copies and a local server standing in for downloads.
- Platform: Windows first; Linux/macOS must not break (LibreOffice install feature may be Windows-only, with "use the
  installed LibreOffice" elsewhere).

## Decided

- Policy per wiki: leave as is / externalize / internalize; applied automatically on stop. *(user)*
- Others clone the wikis from Bitbucket; `files/` is committed by default, "keep out of git" is a per-wiki option. *(user)*
- What TW Desk generated from what (source hash per derivative) is recorded **in the wiki** (fields on the derivative
  tiddlers, e.g. `derived-hash`), not per machine, so every clone agrees and nothing is regenerated needlessly; a
  clone without the original file leaves existing derivatives alone. *(Claude's call, follows from the above)*
- Derivatives as separate tiddlers; display is the user's plugin work. *(user)*
- Text extraction from the start, OCR in German and English. *(user)*
- Office slide/page/sheet images via LibreOffice, installable per user from within TW Desk (no admin), not bundled. *(user, with Claude's advice)*
- Naming `<title>/thumb`, `<title>/page/<n>`, `<title>/sheet/<name>/<n>`, `<title>/text`, field `derived-from`. *(Claude's call)*
- Chromium + pdf.js + tesseract.js inside the app instead of ImageMagick/Ghostscript. *(Claude's call)*

## Claude's calls after the builder check (user to confirm while reading)

- **Wikis only stopped by quitting** (autostart): the policy never runs during quit (like auto-commit). Instead it also
  runs **at app start, before autostart**, for every wiki whose policy isn't "leave as is"; pending derivative tiddlers
  are written then too. Moves are crash-safe (write + verify file, then rewrite tiddler, then remove the old file), so a
  half-done move found later is completed or rolled back, never lost.
- **After internalize** the file in `files/` is **kept** (never deleted by TW Desk – other tiddlers or wikitext may
  point at it, and the wiki would otherwise be the only copy). A later externalize reuses an identical file instead
  of creating a clash.
- **A managed wiki that another managed wiki includes** is not externalized: TW Desk shows why ("included by orga –
  its images would break there") and treats it like an included folder (report only).
- **Caps** (configurable per wiki): page images up to 50 pages per document, `/text` up to ~1 MB per document
  (truncated, with a note field). Beyond that only the thumbnail and the summary fields are written.

The interface for wiki plugins (titles, fields, image formats/sizes, filters, rules) is written up for plugin authors
in `2026-11-04-binary-tiddlers-interface.md` next to this file; it is part of this design and the implementation must
match it.

### From the second builder check (Claude's calls)

- **xlsx per tab**: LibreOffice (7.4+) can export each sheet as exactly one PDF page (`calc_pdf_Export` filter option
  `SinglePageSheets`), so one conversion gives one image per tab in sheet order: `<title>/sheet/<sheet name>`
  (no `/<n>`). Sheet names come from the xlsx XML. Very large sheets are scaled down to a maximum image size.
- **Field names are an interface** the user's display plugins build on, so they are fixed here:
  - on every derivative tiddler: `tw-desk-derived: thumb | page | sheet | text`, `derived-from: <original title>`,
    `derived-hash: <sha256 of the original content>`, `page: <n>` (pages), `sheet: <name>` (sheets);
  - on the original: `page-count`, `sheet-names` (TiddlyWiki title list), `text-truncated: yes` when the cap applied.
  - `files/<name>` for externalized content: the binary keeps its own file name (Windows-safe, extension in lower
    case, numbered on clashes). Only a tiddler with base64 inside a `.tid` gets a name derived from its title
    (made file-system safe, extension from the type).
  - Binaries without a `.meta` file are not moved: TiddlyWiki titles them with their full path, so there is no
    title to keep. They are reported as skipped.
- System tiddlers (`$:/…`, e.g. `$:/favicon.ico`) are never externalized and get no derivatives.
- Generated images in `files/.derived` are left alone by internalize.
- Policy runs at app start don't commit; the next commit (manual or auto-commit on stop) picks the change up.
- Writing summary fields onto the original doesn't change `modified`.

### User's answers to the second check

- **Keep it simple for clones**: policy and settings stay local in each machine's `config.json`; whoever runs TW Desk
  on a clone is responsible for what they commit. No cross-machine determinism or shared policy needed. *(user)*
- **Company restrictions unknown**: whether downloads from documentfoundation.org / the OCR data host and running
  programs from `<userData>/tools` are allowed is unknown. Phase 3 starts with a quick throwaway check of the per-user
  LibreOffice install on the user's machine; if it is blocked, phase 3 falls back to "use an installed LibreOffice"
  only. OCR data: try download first; if blocked, bundle deu + eng. *(user: "try later")*

## Left to the builder

Module split (e.g. `src/binaries.js` pure scan/plan logic + main-process wiring), what counts as "binary" (TiddlyWiki's
`$tw.config.contentTypeInfo` encoding `base64` is a good source), thumbnail size/format, the scan interval and its
Settings, the chip text and the Edit-dialog layout, queue/progress display (Log), and whether OCR data is bundled or downloaded.

## Suggested order

1. Scan + chip + policy + externalize/internalize on stop + `files/` git setting (useful on its own).
2. Derivatives for images and PDFs (thumb, pages, text, OCR).
3. Office: text from XML, embedded thumbnails; LibreOffice detection, per-user install, page images.
